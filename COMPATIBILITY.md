# Buff Compatibility Promise

> **Code that compiles on Buff v1.X keeps compiling on all v1.Y (Y > X) releases.**

This document defines Buff's source-level compatibility promise, modeled on [Go's go1compat](https://go.dev/doc/go1compat) and [Rust's stability guarantee](https://doc.rust-lang.org/cargo/reference/semver.html). It is the formal contract between the Buff language and its users.

---

## What Is Covered

The following are guaranteed to remain stable across all `v1.X` releases:

| Category | Stability Guarantee |
|---|---|
| **Syntax** | All keywords, operators, punctuation, and grammar rules are stable. |
| **Type system** | All built-in types (`Int`, `Float`, `String`, `Bool`, `Vector<T>`, `Map<K,V>`, `Option<T>`, `Result<T,E>`, etc.) and inference rules are stable. |
| **Prelude API** | All free functions (`print`, `len`, `range`, `input`, etc.) are stable — signatures unchanged. |
| **Prelude types** | All prelude types (`DateTime`, `Regex`, `URL`, `Hash`, `TCP`, `File`, `Env`, `Channel<T>`, etc.) are stable. |
| **ErrorCode values** | `E10xx` (lex), `E11xx` (parse), `E12xx` (type), `E13xx` (codegen) are **stable forever** — never renumbered, reused, or silently removed. |
| **CLI commands** | `buff build`, `buff run`, `buff check`, `buff new`, `buff fmt`, `buff bench`, etc. — names and core flags are stable. |
| **`.buffhtml` SFC format** | The `<script>buff</script>` + `<template>RSX</template>` + `<style>CSS</style>` structure is stable. |
| **Editions** | Code written for edition `2026` compiles on ALL future Buff versions in edition `2026` mode. |

---

## What Is NOT Covered

The following may change between minor versions without violating this promise:

| Category | Reason |
|---|---|
| **Generated Rust internals** | The Rust source emitted by the transpiler is an implementation detail. It may change to produce better/faster code. Users should never depend on the exact Rust output. |
| **Performance** | No guarantee that code runs at the same speed across versions. Optimizations may change runtime characteristics. |
| **Binary/ABI compatibility** | No guarantee that compiled binaries are ABI-compatible across versions. Recompilation is always required. |
| **Error message text** | The human-readable text of error messages may change for clarity. The ErrorCode and Span are stable; the prose is not. |
| **Experimental features** | Framework crates marked `Status: experimental` (e.g., `buff-tensor`, `buff-ml`, `buff-game`, etc.) may have API changes. These are not covered by the stability promise until they reach `Status: stable`. |
| **WGSL shader output** | The exact WGSL generated by the GPU codegen may change between versions. The GPU execution semantics are stable; the shader text is not. |

---

## Deprecation Process

When a feature needs to be removed or changed in a breaking way, the following process is followed:

1. **Deprecation notice**: The feature is marked with `@deprecated("use X instead")`. The compiler emits a warning when the feature is used.
2. **Warning period**: The deprecation warning persists for **at least 2 minor versions** (e.g., deprecated in v1.25 → warning through v1.26, v1.27).
3. **Removal**: The feature is removed in the next major version (2.0.0) OR in an edition boundary (if the change can be edition-gated).

During the warning period, the feature continues to work exactly as before — only a warning is added.

---

## Exceptions

The following exceptions allow breaking changes outside the normal deprecation cycle:

1. **Security fixes**: If a feature has a security vulnerability, it may be fixed in a patch release even if the fix is technically breaking. Such fixes are documented in the CHANGELOG and announced.

2. **Edition boundaries**: New editions (e.g., edition `2028`) may introduce breaking syntax changes. However, code written for the old edition continues to compile. Editions are opt-in via `edition = "2028"` in `buff.toml`.

3. **Compiler bugs**: If the compiler accepts code that it should have rejected (a bug), fixing the compiler to reject that code is not considered a breaking change. However, such fixes are documented and given a deprecation period when feasible.

---

## Semantic Versioning

Buff follows [SemVer 2.0](https://semver.org/):

- **MAJOR (2.0.0)**: Reserved for the first genuinely breaking change that can't be edition-gated. Not planned for v1.x.
- **MINOR (1.25.0, 1.26.0, ...)**: New features, additions, deprecation notices. Fully backwards-compatible.
- **PATCH (1.25.1, 1.25.2, ...)**: Bug fixes, security patches, documentation. Fully backwards-compatible.

---

## 2.0.0 Trigger

Version 2.0.0 is reserved for the first change that:
- Breaks source compatibility for code in the current default edition, AND
- Cannot be edition-gated (i.e., the change affects fundamental syntax or semantics that can't be opt-in).

This is not planned for the foreseeable future. The edition mechanism is preferred for all breaking changes.
