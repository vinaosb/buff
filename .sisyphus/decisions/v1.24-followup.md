## F1 — `DataFrame.to_json()` missing (T22-FU1)

- **Finding:** The `buff-dataframe` public surface (25 fns at the cap) has
  only `to_table_string()` for human-readable output. There is no JSON
  serializer; users must iterate rows + dispatch on `Series.kind()` + use
  the stdlib `JSON` module (see the `rows_to_json` helper in
  `examples/integration/dataframe_to_json.buff`).
- **Why non-trivial:** The 25-fn cap has zero headroom. Adding `to_json()`
  requires either raising the cap (API surface change) or replacing an
  existing less-used method, plus a codegen lowering arm.
- **Recommended action:** Add `DataFrame.to_json() -> String` (or
  `to_json_lines() -> String`) to `buff-dataframe`, OR add
  `JSON.from_dataframe(df)` to the stdlib `JSON` module.
- **Estimate:** ~80-120 LOC (crate + prelude/codegen wiring).
- **Target:** **v1.25** (unblocks every notebook/dataset export — the
  single most user-visible gap per the T22 report).

## F2 — `Type::Tensor` variant + instance-method codegen (T22-FU2)

- **Finding:** Only the four `Tensor` assoc fns (`zeros`/`ones`/`from_vec`/
  `filled`) are registered; the 20 instance methods (`matmul`, `as_slice`,
  `shape`, …) return `Type::Unknown` at the type-checker level. Mirrors
  the T8/T11/T12 forward-declaration precedent.
- **Why non-trivial:** Coordinated sibling task across
  `buff-lang-types/src/ty.rs` + `buff-lang-codegen-rust/src/rust_codegen.rs`
  — outside any single framework crate's shared zone.
- **Recommended action:** Add `Type::Tensor` variant + instance-method
  codegen lowering arms for the 20 Tensor instance methods enumerated in
  `crates/buff-tensor/src/lib.rs`.
- **Estimate:** ~400-600 LOC.
- **Target:** **v1.25** (gating dependency for end-to-end `buff run` of
  tensor examples).

## F3 — `DataFrame.from_rows` named-arg codegen validation (T22-FU3)

- **Finding:** Buff convention §11 mandates named args for multi-arg calls.
  Whether the T7 codegen lowering arm for `(DataFrame, FromRows)` honors
  named-arg dispatch is unverified. The underlying Rust signature is
  positional; the codegen layer must map named → positional by parameter
  name.
- **Why non-trivial:** Requires validating/extending the codegen
  dispatcher.
- **Recommended action:** Validate the `(DataFrame, FromRows)` codegen arm
  honors named-arg call shape per Buff convention §11; extend the
  dispatcher if not.
- **Estimate:** ~30-80 LOC (depending on whether the dispatcher already
  handles it).
- **Target:** **v1.25** (pin BEFORE flagship data-analysis cells multiply
  the ambiguity).

## F4 — `AggOp` enum syntax pinning (T22-FU4)

- **Finding:** `GroupBy.agg(col, op)` takes an `AggOp` enum
  (`Sum`/`Mean`/`Min`/`Max`/`Count`). Two candidate syntaxes
  (`AggOp.Mean` dotted access vs. string-form `agg(col, "mean")` lowered
  via the existing `AggOp::parse` helper) — no canonical Buff syntax is
  pinned today.
- **Why non-trivial:** Cross-cutting language-surface decision; needs a
  convention-doc update + codegen pick.
- **Recommended action:** Pin the canonical form; document it in
  `crates/buff-dataframe/AGENTS.md` and `.sisyphus/plans/buff-conventions.md`.
- **Estimate:** ~40-100 LOC.
- **Target:** **v1.25** (pin BEFORE the flagship's `group_by(...).agg(...)`
  examples multiply the ambiguity).

## F5 — Multi-threaded `Signal` for reactive+web (T22-FU5)

- **Finding:** `buff-reactive` uses `Rc<RefCell<T>>` internals — types are
  NOT `Send + Sync`. `buff-web` requires `Handler = Arc<dyn Fn(Request) ->
  Response + Send + Sync>` because handlers run on tokio worker threads.
  Direct sharing of a `Signal<T>` across web handlers fails the bound at
  compile time.
- **Why non-trivial:** Threading-model decision with three options on the
  table (wait for v1.18+ `Arc<Mutex<T>>` Signal; thread-local relay via
  single-threaded tokio; wrap at the call site). The T22 report
  recommends option (b) (thread-local relay) as the smallest delta.
- **Recommended action:** Pick option (b) for the flagship; document the
  single-threaded constraint. Land the v1.18+ multi-threaded `Signal`
  (`Arc<Mutex<T>>` / `arc-swap`) as the long-term fix.
- **Estimate:** option (b) ~150-250 LOC; full multi-threaded Signal
  ~600-900 LOC.
- **Target:** option (b) **v1.25**; full multi-threaded `Signal` **v1.26+**
  (matches the `buff-reactive` AGENTS.md "DEFERRED" section).

## F6 — `buff-ml` bias-gradient 3x factor

- **Finding:** The autodiff bias gradient is ~3x the analytical value for
  batch>1 (likely a `sum_axis` shape issue in `buff-tensor`). Training
  convergence tests pass despite this. Documented in
  `crates/buff-ml/AGENTS.md` "KNOWN ISSUES".
- **Why non-trivial:** Requires debugging the autodiff + tensor shape
  interaction; the fix likely touches both `buff-ml/src/autodiff.rs` and
  possibly `buff-tensor/src/math.rs`.
- **Recommended action:** Trace the bias-gradient path for batch>1; fix the
  `sum_axis` shape reduction so the gradient matches the analytical value.
- **Estimate:** ~50-150 LOC.
- **Target:** **v1.25** (correctness fix — currently masked by convergence
  tests but produces wrong gradients).

## F7 — Codegen lowering for ALL framework `Type` variants (the long-pole)

- **Finding:** End-to-end `buff run` execution of every v1.14–v1.23
  framework example is blocked by a single coordinated sibling task: adding
  the `Type::{DataFrame, Tensor, Pipeline, Signal, Computed, Effect, Web,
  Image, AudioBuffer, …}` variants to `buff-lang-types/src/ty.rs` plus
  their instance-method codegen lowering arms in
  `buff-lang-codegen-rust/src/rust_codegen.rs`. Today all framework
  examples PARSE and pass `buff check`, but `buff run` cannot execute them.
- **Why non-trivial:** This is the gating dependency for the flagship's
  "runs end-to-end" exit criterion. Large surface — one `Type` variant +
  N lowering arms per framework crate. Tracked as a cross-cutting effort.
- **Recommended action:** Land the Type variants + lowering arms
  incrementally per framework crate (start with DataFrame + Tensor +
  Pipeline + Web + Reactive to unblock the flagship). This is the
  umbrella item under which F2, F3, F4 all live.
- **Estimate:** ~2000-4000 LOC total (across all framework crates).
- **Target:** **v1.25–v1.27** (staged; flagship-blocking subset in v1.25).

## F8 — Full code-comment version-scoping audit

- **Finding:** `grep -rn 'v0\.1\b|v0\.5\b' crates/` returns 138 matches
  across 26 files. Most are **legitimate** version-scoped documentation
  ("preserves the v0.1 behavior", "v0.5 doesn't track range types",
  "the v0.5 fallback"). Some v0.5-era limitations may have been lifted in
  v1.0–v1.24, but determining which requires per-comment judgment and
  risk of semantic drift.
- **Why non-trivial:** Per-comment judgment; high blast radius; not a
  mechanical find-replace.
- **Recommended action:** A dedicated pass to audit each v0.1/v0.5
  version-scoped comment and update the ones whose limitation has been
  lifted. Low priority — these are documentation accuracy, not behavior.
- **Estimate:** ~200-400 LOC (only the genuinely-outdated subset).
- **Target:** **v1.26+** (hygiene; not blocking).

## F9 — Exhaustive `unwrap`/`expect`/`panic!` audit in non-test `src`

- **Finding:** `grep -rn 'unwrap()\|expect()\|panic!' crates/` returns
  5170 matches across 480 files — overwhelmingly in `tests/` and in
  documentation strings ("No unwrap…"). CI enforces
  `clippy --all-targets -D warnings` (which includes
  `clippy::unwrap_used` / `expect_used` / `panic` where configured), so
  the hard rule is enforced automatically. A full manual filter to confirm
  zero violations in non-test `src` is non-trivial.
- **Why non-trivial:** 5170 matches to triage (filter out tests + doc
  strings); CI clippy is the authoritative enforcement.
- **Recommended action:** Trust CI clippy enforcement; no action needed
  unless a specific violation is reported. Optionally add a
  `#![warn(clippy::unwrap_used)]` crate-level lint to make enforcement
  explicit (low LOC, high value).
- **Estimate:** ~20-50 LOC if adding crate-level lints; otherwise 0.
- **Target:** **v1.26+** (optional hardening).

## F10 — Per-crate `README.md` for ~24 remaining crates

- **Finding:** After T28, 31 crates still lack a per-crate `README.md`. Of
  these, ~24 are the core compiler + tooling crates (`buff-lang-*`,
  `buff-lsp`, `buff-eval`, `buff-repl`, `buff-jupyter`, `buff-registry`,
  `buff-playground-wasm`, `buff-ui-dioxus`, `buff-plugins`, `buff-dap`,
  `bufflings`, `buff-msgpack`, `buff-xml`, `buff-http-client`,
  `buff-actors`, `buff-crypto-extras`, `buff-geo`, `buff-simd`,
  `buff-web3`). The core compiler crates are intentionally covered by the
  root README/AGENTS, but the tooling/framework ones would benefit from a
  per-crate README.
- **Why non-trivial:** 24 files × ~40-60 LOC each ≈ 1000-1400 LOC — would
  blow the v1.24 5000-LOC budget if combined with everything else, and
  exceeds the "trivial per fix" threshold when batched.
- **Recommended action:** Add per-crate README.md for the tooling + stdlib
  framework crates in a follow-up (each crate already has a well-documented
  `lib.rs` header to source from).
- **Estimate:** ~1000-1400 LOC.
- **Target:** **v1.26+** (nice-to-have; the root README + per-crate
  AGENTS.md already cover discoverability).
