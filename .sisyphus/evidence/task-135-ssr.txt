## 2. Dioxus SSR API used

Researched via background librarian (task `bg_695b5990`, session `ses_07c84034dffeBjfBVKBJ5wQyDb`, 2m37s). Synthesis:

- **Crate:** `dioxus-ssr` (separate from the `dioxus` umbrella; workspace pin tracks the umbrella minor).
- **Entry point:** `dioxus_ssr::render(&VirtualDom) -> String` (the convenience function used by `buff-ui-dioxus::render_to_string`).
- **VirtualDom construction:** `VirtualDom::new(root: fn() -> Element) -> VirtualDom` (NOTE: takes a raw `fn()` pointer, not a generic — caught + corrected during first build attempt).
- **Initial render:** `vdom.rebuild_in_place()` runs every effect + memo once so signals settle at their initial values; the resulting dom is then safe to hand to `dioxus_ssr::render`.
- **Event handlers:** ignored during SSR (no user to click). `use_signal` initial values ARE rendered.
- **Cargo dep:** `dioxus-ssr = "0.7"` — no feature flags required. Pure-Rust, no native deps.
- **Verified working:** `cargo tree -p buff-ui-dioxus --depth 1` shows `dioxus v0.7.9` + `dioxus-ssr v0.7.9` transitively resolved (Cargo.lock updated automatically).

The `render_to_string` helper signature:

```rust
pub fn render_to_string(root: fn() -> Element) -> String {
    let mut vdom = VirtualDom::new(root);
    vdom.rebuild_in_place();
    dioxus_ssr::render(&vdom)
}
```

This is the minimal host-side surface T133-generated `.buffhtml` code + the `buff ssr` CLI subcommand lower onto.

## 3. CLI subcommand design

### Shape

```
buff ssr <FILE.buffhtml> [--output <PATH>] [--release]
```

Mirrors the existing `buff build` / `buff run` shape:
- `<FILE>` is a `.buffhtml` Single-File Component (T133).
- `--output <PATH>` writes the HTML to `<PATH>` instead of stdout.
- `--release` selects release-grade rustc flags (`-C opt-level=3 -C lto=fat -C codegen-units=1`); default is fast-debug.

### Pipeline (commands/ssr.rs::run)

1. **Parse + codegen** via the existing T133 path `pipeline::compile_buffhtml_to_rust(file)` → `BuffHtmlCompileOutput { rust_source, rust_file_path, span_map }`.
2. **Extract component fn name** from the generated Rust source via `extract_component_name` (walks the token stream looking for `#[component] fn <Name>`).
3. **Splice the SSR driver main** via `format_driver_source`: appends
   ```rust
   use buff_ui_dioxus::*;
   use buff_ui_dioxus::dioxus::prelude::*;

   fn main() {
       let html = buff_ui_dioxus::render_to_string(<Name>);
       print!("{html}");
   }
   ```
   to the codegen-buffhtml output.
4. **Write the driver .rs** to a unique-per-invocation path alongside the input (process ID + thread ID in the filename so concurrent invocations stay isolated).
5. **Compile via rustc** (host target; Debug or Release from `--release`) using `pipeline::compile_buffhtml_rust_to_exe` so rustc diagnostics are reverse-mapped to `.buffhtml` line:col via the `SpanMap` side-table (T133).
6. **Run the binary**, capture stdout (the rendered HTML).
7. **Clean up** the driver `.rs` + the binary (mirrors `buff run`'s cleanup-on-exit stance).
8. **Forward the HTML** to the user's stdout OR write to `--output <PATH>`.

### Why this shape (not a direct interpreter)

Two design options were considered:
- **Option A — Direct template interpreter:** parse `.buffhtml` → interpret the AST → emit HTML directly (skip Rust codegen entirely). Faster iteration, but a parallel codegen path that must stay byte-identical to the wasm path (otherwise hydration breaks — see USER ACTION recipe §5.1).
- **Option B — Compile + run (SHIPPED):** parse + codegen + compile + run a small SSR driver binary. Reuses the existing T133 + rustc pipeline 100%, so the rendered HTML is byte-identical to what the wasm client would render (modulo the deterministic-rendering caveats documented in the hydration recipe).

Option B wins because the byte-identical guarantee is the load-bearing property for hydration; Option A would have introduced a third rendering path (alongside the T121b wasm path + the T133 codegen path) with no upstream check that they agree. The compile cost (~3-5s for the SSR driver) is acceptable for the SSR use case (one-shot render, not a tight loop).
