WHAT THIS TASK DID
------------------
Wired the Jupyter `execute_request` handler from a stub ("execution not yet
implemented (T129b)") to a REAL Buff evaluation engine reusing buff-eval
(T125). The kernel now owns an `Evaluator` in its session state, so cells
accumulate `let`-bindings and `func` declarations across `execute_request`
calls — exactly the same accumulating session the REPL uses. Output is
emitted via iopub `stream` (stdout/stderr) and `execute_result`
(text/plain). Errors are surfaced as iopub `error` messages with
ename/evalue/traceback AND `execute_reply` with status=error — the kernel
SURVIVES errors and keeps serving subsequent cells.

        4. Normalize code to end with `\n` (mirrors buff-repl's

        5. Call `evaluator.eval_line(&code)` (blocking — spawns rustc

             traceback=stderr lines + diagnostic) + execute_reply
             status=error.
           - Clean run, value Some(v) → iopub `execute_result` with
             text/plain (suppressed stream to avoid duplicating the
             wrapper-print's stdout).
           - Clean run, value None + stdout non-empty → iopub `stream`
             (stdout).
           - Captured stderr non-empty → iopub `stream` (stderr).

        8. shell `execute_reply` (status ok OR error).

      failure the loop continues.

BUFF-EVAL / BUFF-REPL API REUSED
--------------------------------
The buff-jupyter kernel CONSUMES buff-eval's public API; it does NOT
reimplement evaluation. The reuse surface:

- `buff_eval::Evaluator::new() -> Evaluator`
    Construct a fresh evaluator with empty session state. Used in
    `Kernel::new`.
- `buff_eval::Evaluator::eval_line(&mut self, line: &str) -> EvalResult`
    Evaluate one cell's source against the accumulating session state.
    `let` bindings and `func` declarations persist across calls. This
    is the persistent-session entry point required by T129b. (The
    `eval()` method is functionally identical — the split documents
    intent; we use `eval_line` to mirror buff-repl's terminology.)
- `buff_eval::EvalResult { value, stdout, stderr, diagnostic, exit_code }`
    The kernel branches on:
      * `result.diagnostic.is_some() || result.exit_code != Some(0)` →
        error path (iopub `error` + execute_reply status=error).
      * `result.value.is_some()` → bare-expression path (iopub
        `execute_result`).
      * Non-empty stdout (with no value) → iopub `stream` (stdout).
      * Non-empty stderr → iopub `stream` (stderr).
- The evaluator's pipeline is `tokenize → parse → generate_rust →
  rustc --edition 2021 -O → spawn-and-capture`. buff-jupyter adds NO
  new compilation logic.

buff-repl is NOT consumed directly (it would pull in rustyline which
is unnecessary for the kernel). The kernel mirrors buff-repl's
trailing-`\n` normalization (from `handle_action::ReplAction::Eval`)
inline.

NO API GAPS encountered: buff-eval provides exactly the
persistent-session surface T129b needs (`Evaluator::new` + `eval_line`
+ `EvalResult`).

KNOWN LIMITATIONS / API-GAP NOTES
---------------------------------
1. State pollution on parse-error cells (buff-eval limitation).

   buff-eval's Evaluator accumulates BodyStmt-snippets BEFORE running
   the composed program. When a cell like `func (` fails to parse,
   the broken source IS appended to the session's body_stmts_src;
   subsequent cells fail to compile because the broken source
   pollutes the composed program.

   This is the SAME behavior as the buff-repl (T125a) — buff-repl's
   handle_load_command even has explicit handling for the
   "empty-main artifact" diagnostic this produces. The
   acceptance criterion "kernel MUST survive errors and keep serving
   subsequent cells" is MET (the kernel processes subsequent
   requests and returns replies — possibly error replies if the
   state is polluted). The stronger guarantee "subsequent VALID
   cells execute cleanly despite earlier errors" is NOT met due to
   buff-eval's lack of snapshot/rollback on the Evaluator (the
   struct's fields are private and it deliberately does NOT derive
   Clone).

   Workaround for users: restart the kernel via the Jupyter UI
   (Kernel > Restart) to get a clean Evaluator. Documented in the
   kernel.rs docstring for `handle_execute_request`.

   NOT FIXED in T129b because fixing it would require either:
   (a) Modifying buff-eval's source to expose a snapshot/restore API
       (out of scope — the task forbids touching buff-eval source).
   (b) Re-implementing the Evaluator's classify logic in buff-jupyter
       to pre-validate before accumulating (significant duplication).
   (c) Tracking successful cells in the kernel and re-running them
       on error (O(N²) rustc spawns — too slow for real notebooks).

   Post-T129c work could add a snapshot/restore API to buff-eval.

2. Blocking evaluation.

   `Evaluator::eval_line` is synchronous (spawns rustc + binary via
   std::process::Command). The kernel's tokio loop blocks during
   evaluation — fine for a single front-end, but a concurrent
   multi-front-end scenario would stall. Concurrent hardening
   (heartbeat task, multi-front-end) is post-T129c work, flagged in
   the kernel.rs docstring.

3. No `input_request` / interactive stdin.

   The T129a scaffold does not bind the stdin socket. T129b does not
   change this — `allow_stdin=true` in execute_request is silently
   ignored (no Buff `input()` builtin exists in the prelude yet
   either). Lands in T129c+.
