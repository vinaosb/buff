SUMMARY
-------
Added rich display + introspection to the Buff Jupyter kernel:

1. Vector / Matrix literals now render as a Jupyter MIME bundle:
   `execute_result` content.data = {
       "text/html":  "<table>...</table>",
       "text/plain": "[1, 2, 3]"   // mandatory fallback
   }
   Both MIME types are ALWAYS emitted together (HTML never travels
   alone — terminal / screen-reader / text-only nbconvert exporters
   must still see a meaningful rendering).

2. `?name` magic: surfaces resolved type info as execute_result
   text/plain. Format: `"name: <Type>"`. Uses only
   `Evaluator::type_of` — no rustc spawn.

3. `??name` magic: surfaces best-available definition text
   (type + current value) as execute_result text/plain.
   Format: `"name: <Type>\n= <value>"`. Calls `eval_line(name)`
   to capture the value via the standard compile-and-run path.

4. New `DisplayData` struct added to messages.rs (for future
   `display_data` msg-type support; the current kernel emits
   `execute_result` for trailing bare-expr values, which is the
   spec-accepted deliverable).

5. New `ExecuteResult::mime_bundle` + `ExecuteResult::html_with_plain`
   constructors (and matching `DisplayData::html_with_plain`).

IMPLEMENTATION NOTES
--------------------
- Vector/Matrix detection uses `Evaluator::type_of(trimmed_code)`
  → `Option<ResolvedType>`. When the resolved type is `Vector<_>` or
  `Matrix<_>` AND the source is a `[...]`-shaped literal, the kernel
  takes the "rich-display-literal shortcut" — it renders the HTML
  table FROM SOURCE and SKIPS the rustc spawn entirely. This works
  around Buff's codegen gap: `print(vec)` lowers to Rust's
  `println!("{}", vec)` which fails to compile today because
  `Vec<T>` doesn't impl `Display`. The workaround avoids wasting a
  rustc spawn on a known-broken path; the codegen fix is tracked as
  post-T129c work in buff-lang-codegen-rust.

- Non-literal Vector/Matrix expressions (e.g. `[1,2,3].map(...)`)
  fall through to the normal compile-and-run path. If they yield a
  value, the kernel renders it as a MIME bundle from the captured
  stdout. If they fail (Display gap), the kernel surfaces the error
  normally — no rich rendering, no surprise.

- HTML table formatter (`format_rich_html`) handles both 1-D
  (Vector) and 2-D (Matrix) shapes:
    * 1-D `[1, 2, 3]`           → single row of 3 <td> cells.
    * 2-D `[[1, 2], [3, 4]]`    → 2 rows, 2 cells each.
  Cells are HTML-escaped (`&`, `<`, `>`, `"`, `'`) so numeric and
  string content renders safely.

- Introspection parser (`parse_introspection`) checks `??` BEFORE
  `?` (longer-prefix-first) so `??x` classifies as Source (not
  Help-of-"?x"). The name is validated as a Buff identifier
  (alphabetic / `_` start; alphanumeric / `_` tail; Unicode
  alphabetic chars accepted — Buff's PT-BR naming convention).

- `??name` evaluates the name via `eval_line` — this DOES spawn
  rustc (~3s). BareExpr evaluation does NOT accumulate state, so the
  query has no side effects on subsequent cells.

LIMITATIONS (documented, accepted for T129c)
--------------------------------------------
- `??name` does NOT surface the original source line of the binding
  because `Evaluator`'s accumulated `body_stmts_src` /
  `top_level_src` are private. Best-available definition text is
  type + current value. Extracting source requires enhancing
  buff-eval's public API (post-T129c follow-up).

- Image/PNG rendering for GPU matrices is OUT OF SCOPE — the
  runtime does not currently expose raster bytes. HTML `<table>`
  rendering is the accepted deliverable for matrices.

- ipywidgets, kernel-timeout handling, and interactive input_request
  over the stdin socket are out of scope (post-T129c).
