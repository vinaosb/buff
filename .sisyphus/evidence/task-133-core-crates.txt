================================================================================
AST SHAPE — what was chosen + why
================================================================================

A new SIBLING crate (`crates/buff-lang-ast-rsx/`) ships the AST node
hierarchy. This was the preferred option per the task spec (mirrors the
decision record §4 "MINOR — add RsxTemplateFile in a new sibling crate"
rationale): the existing `buff-lang-ast` crate is depended on by
lexer/parser/types/codegen-rust and any change there would ripple. The new
crate is depended on ONLY by `buff-lang-buffhtml-parser` and
`buff-lang-codegen-buffhtml` — zero churn for existing compiler code.

The node hierarchy:

  RsxTemplateFile
  ├── script: Option<ScriptBlock>   (top-level <script lang="buff"> block)
  ├── root: Vec<RsxNode>            (body fragment — Svelte-style)
  └── span: Span

  RsxNode (enum, one per floor-grammar construct):
  ├── Element(RsxElement)           (HTML element OR child component, flagged)
  ├── Fragment(RsxFragment)         (<> ... </>)
  ├── Text(RsxText)                 (raw text run)
  ├── Interp(RsxInterp)             ({expr} — expr stored as RAW source text)
  ├── If(RsxIf)                     ({#if}/{:else if}/{:else}{/if})
  ├── Each(RsxEach)                 ({#each iterable as binding}{/each})
  ├── Slot(RsxSlot)                 (<slot />)
  ├── Comment(RsxComment)           (HTML + Buff directive comments unified)
  └── Script(ScriptBlock)           (only legal at file top level)

Key design decisions:

  1. RsxInterp stores RAW SOURCE TEXT, not a parsed `buff_lang_ast::Expr`.
     Rationale: T133's job is to PROVE the codegen pipeline works end-to-end
     (decision record §6 MUST-ship). Delegating `{...}` contents to Buff's
     existing expression parser is part of T121b's "MAY" stretch list (it
     requires figuring out how to splice a `buff_lang_ast::Expr` into a Rust
     `quote!{}` TokenStream — non-trivial, and the codegen today emits the
     raw expression source verbatim, which is what T121b does anyway). T134
     will tighten this to use `buff_lang_ast::Expr` for type checking.

  2. RsxElement carries `is_component: bool` (uppercase first char). Codegen
     branches on this: components emit `Counter { ... }` (Dioxus component
     invocation), host elements emit `div { ... }` (Dioxus HTML tag).

  3. RsxAttribute is an enum of 5 variants (Literal / Expression / Event /
     NamedProp / Boolean) so each form gets first-class lowering without
     type-heuristic dispatch in codegen.

  4. Every node carries `span: Span` (re-exported from `buff_lang_error` for
     consistency with the existing AST crate). No spanless nodes.

  5. Deferred constructs are NOT in the enum — the parser emits a
     `BuffHtmlParseError` with a "deferred to T134+" message at lex/parse
     time, rather than silently dropping them.

================================================================================
SPAN-MAPPING IMPLEMENTATION APPROACH
================================================================================

The recommended strategy from the spike (evidence file §"RECOMMENDED
SPAN-MAPPING STRATEGY") is **post-format text-region reverse mapping**:

  1. AST enrichment (parser): every expression-bearing node carries a
     `Span` from the lexer (byte offsets + SourceId). DONE — `RsxInterp.span`,
     `RsxAttributeKind::Expression.expr_span`, `Event.handler_span`,
     `NamedProp.value_span`, etc.

  2. Codegen emission (lib.rs): while lowering each construct, the codegen
     calls `SpanMapBuilder::add_anchor(anchor_text, buffhtml_span)` to record
     a tuple of `(stable_substring, source_position)`. `anchor_text` is
     typically the first identifier of the expression (e.g. `count` for
     `{count}`), chosen because prettyplease never modifies identifier
     characters. DONE.

  3. Post-format scan (span_map.rs `SpanMapBuilder::finalize`): after
     `prettyplease::unparse(&file)` produces the formatted `.rs` text, the
     builder walks the text line-by-line, finds each anchor's
     `(line, col)` via substring search, and assembles a sorted
     `Vec<(RsLineCol, BuffHtmlSpan)>` — the `SpanMap`. DONE.

  4. Diagnostic remapping (SpanMap::map_span): given a rustc diagnostic
     `(rs_line, rs_col)` (1-based, matching rustc output), binary-search the
     sorted anchor table for the largest `(RsLineCol ≤ query)` and return
     the originating `.buffhtml` span. DONE — `pub fn map_span(line, col)
     -> Option<Span>`.

The CLI's error_mapper (`crates/buff-lang-cli/src/error_mapper.rs`) is the
downstream consumer — it will translate rustc's `--> generated.rs:LINE:COL`
into `--> Counter.buffhtml:mapped_line:mapped_col` using `SpanMap::map_span`.
That CLI wiring is a separate T133 sub-task (per task brief MUST NOT #4:
"Do NOT attempt to wire into `buff build`/`buff run`/`buff check`").

The spike's "degradation path" (filename translation + TODO marker) is the
documented fallback if a particular anchor can't be located in the post-format
text — see `SpanMapBuilder::finalize` method doc.

Granularity matches the spike's table:

  | Construct                | Anchored?      | map_span resolution   |
  |--------------------------|----------------|-----------------------|
  | `{expr}` interpolation   | YES (per-expr) | exact token           |
  | `attr={expr}`            | YES            | exact token           |
  | `on:event={closure}`     | YES (handler)  | exact token           |
  | `<Component />` tag name | YES (tag)      | block-level fallback  |
  | `{#each items as item}`  | YES (iter)     | iterable-expression   |
  | Generated boilerplate    | NO             | block-level fallback  |

Test coverage (`span_map.rs` unit tests + `codegen_tests.rs`
`span_map_map_span_returns_buffhtml_position`):
  - empty builder → empty map
  - multiple anchors → nearest-preceding binary search works
  - missing anchor text silently dropped (graceful degradation)
  - whitespace-only anchor ignored (no false positives)
  - out-of-order anchors sorted ascending (dedupe by RsLineCol)

================================================================================
OPEN QUESTIONS / KNOWN LIMITATIONS
================================================================================

1. Script block is preserved as `const __BUFF_SCRIPT_SOURCE: &str` — the
   generated file is a valid `syn::File`, but downstream code does NOT yet
   invoke `buff-lang-lexer` + `buff-lang-parser` to extract the component
   logic. That wiring is the CLI integration step (T133 sub-task per task
   brief MUST NOT #4).

2. `{expr}` interpolation stores RAW source text. This means a Buff
   expression like `user.name.upper()` is emitted verbatim into the
   `rsx!{}` TokenStream where Rust will parse it as a Rust expression. Most
   overlapping syntax works (identifiers, method calls, arithmetic). Divergent
   syntax (e.g. Buff's `?.` null-conditional, `|>` pipeline) will fail at
   Rust compile time with a span the side-table can map back. T134 will
   lower through `buff_lang_ast::Expr` for type-checked codegen.

3. Event modifiers (`on:submit_prevent`) are PARSED and the modifiers list is
   captured in `RsxAttributeKind::Event.modifiers`, but T133 codegen does NOT
   yet wire them (no `.prevent_default()` call in the generated closure). The
   `on_submit` attribute name is emitted with the BASE event name only.
   Documented as TODO at the `lower_attr` Event arm.

4. `{#each}`'s `{:else}` branch is captured in the AST but NOT lowered — T133
   codegen emits the iterator alone. Documented as TODO at `lower_each`.

5. `<slot />` always lowers to `{ children }` — it assumes the parent
   component declares `children: ReadOnlyChildren`. If the user's script block
   doesn't bind `children`, rustc emits E0425 that the side-table maps to the
   slot's span.

6. Span-map lookup is bounded by anchor *textual* presence in the formatted
   `.rs` output. If two interpolations use the same identifier (e.g.
   `{count}` and `{count + 1}` both anchored on `count`), only the first
   occurrence in `.rs` text is anchored. Mitigation: future work can anchor
   on longer token sequences (e.g. `count + 1` for the second one) or use
   sentinel-comment markers (T134+).
