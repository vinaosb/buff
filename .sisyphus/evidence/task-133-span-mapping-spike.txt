VERDICT: **PASS** (with implementation nuance documented below)
================================================================================

**Core question (Oracle §7 trigger #2):** "If Dioxus's `Location` API cannot
carry `.buffhtml` source positions, error messages will be unusable."

**Answer:** rustc errors inside `rsx!{}` CAN be mapped to `.buffhtml` source
positions. The dioxus-rsx proc-macro preserves input TokenStream spans via
`quote_spanned!{ token.span() => ... }` throughout its expansion (verified by
source-code inspection of `packages/rsx/src/{attribute,component,ifmt,
diagnostics}.rs` in dioxus 0.7.2). Rustc diagnostics therefore point at the
exact line:col of the offending token in the *generated .rs file*. Mapping
that back to `.buffhtml` is a deterministic text-region reverse-mapping
problem — fully solvable inside `buff-lang-codegen-buffhtml` without compiler
hacks, without `Location::caller()` plumbing, and without changing the
dioxus-rsx proc-macro.

**Oracle hypothesis verification:**
- "Dioxus `rsx!{}` supports `Location` callers — wire them through."
  → **Partially correct, but unnecessary.** Dioxus *does* use
  `std::panic::Location::caller()` extensively (found in `signals`,
  `hooks`, `generational-box`, `stores`), but those resolve to
  `file!()`/`line!()`/`column!()` at the *generated .rs site*. They serve
  runtime debug-diagnostics (e.g. "signal created at app.rs:42"), not
  compile-time rustc spans. Wiring Buff source positions through them would
  not help because they are already at .rs granularity, identical to what
  rustc itself reports. **Recommendation: skip `Location::caller()` entirely;
  it adds complexity without solving the mapping problem.**
- "Carry forward T121b's span-preservation approach."
  → **Correct.** T121b documented that proc_macro2::Span on tokens inside the
  macro body "point at the generated Rust text." This spike confirms that
  those generated-text spans are *preserved by the dioxus-rsx proc-macro
  into its expansion*, so rustc diagnostics land at precise generated-text
  positions.

**Span mapping analysis:**
- **Diagnostic #1** (`21:5` → `26:6`): macro-call-site span. The full
  `rsx!{}` invocation block. Useful for "this error originates in your
  view block at buffhtml line X" — coarse but always available.
- **Diagnostic #2** (`24:13`): **TOKEN-LEVEL span.** Points at the exact
  column where the broken interpolation literal begins. The dioxus-rsx
  proc-macro's expansion of the format string `"Increment {x}"` into
  `::std::format!("Increment {}", x)` preserved the input token span on the
  literal, so when rustc fails to resolve `x`, it underlines the original
  user-written string.
- **Buffhtml mapping:** `(undefined_var.rs:24:13)` → reverse-lookup in
  codegen side-table → `(Counter.buffhtml:line_of_<span>)`. Trivial.

================================================================================
RECOMMENDED SPAN-MAPPING STRATEGY for `buff-lang-codegen-buffhtml`
================================================================================

The strategy is **post-format text-region reverse mapping** (T121b
"mitigation #2" refined). It works because:

  (a) Buff controls the codegen: we know each token's origin in `.buffhtml`.
  (b) `prettyplease::unparse` produces deterministic output — same input AST
      → byte-identical .rs text.
  (c) After prettyplease, we can scan the .rs text for anchors that we placed
      during codegen, recording their (rs_line, buffhtml_line, buffhtml_col)
      tuples. When a rustc diagnostic arrives with (rs_line, rs_col), binary
      search the anchor table for the nearest preceding anchor; remap.

**Concrete steps (in order of codegen):**

1. **AST enrichment** (`buff-lang-buffhtml-parser`): every expression node
   inside `{...}` interpolation, every attribute value, and every event
   handler carries a `(buffhtml_byte_offset, buffhtml_line, buffhtml_col)`
   triple from the lexer.

2. **Codegen emission** (`buff-lang-codegen-buffhtml`): for each lowered
   construct, emit it into the `syn` tree AND record an anchor:
   ```rust
   struct Anchor {
       rs_token_seq: Vec<TokenGram>,  // fingerprint of emitted tokens
       buffhtml_span: Span,            // original .buffhtml position
   }
   ```
   To make anchors robust against prettyplease's whitespace reflow, prefer
   anchoring on **identifier or literal content** (which prettyplease never
   modifies), not on punctuation spacing.

3. **Post-format scan**: after `prettyplease::unparse(&file)`, walk the .rs
   source line-by-line. For each anchor in the table, find the line:col of
   its token-gram in the .rs text. Build a sorted `Vec<(RsLineCol, BuffHtmlSpan)>`.

4. **Diagnostic remapping** (`buff-lang-cli/src/error_mapper.rs`, extended
   for `.buffhtml`): when rustc emits `--> <gen_path>.rs:LINE:COL`:
   - Translate the filename: `<gen_path>.rs` → original `.buffhtml` path
     (via codegen manifest written alongside the .rs file).
   - Binary-search the anchor table for the largest `(RsLineCol ≤ error)`.
   - Emit `--> Counter.buffhtml:mapped_line:mapped_col`.
   - If no anchor covers the region (e.g., error in generated boilerplate
     outside any user construct), fall back to the enclosing `rsx!{}`
     block's span (always available — emit as a `TODO(buffhtml-span)` note
     per Oracle §5 mitigation).

5. **Boilerplate suppression** (stretch goal): rustc errors that originate
     in dioxus's macro-expansion chains (e.g., the `SuperFrom` trait-bound
     cascade in Experiment 3) should be filtered or summarized. The
     diagnostic's primary span at the user token is preserved; secondary
     spans into `dioxus-core`/`dioxus-html` registry crates are dropped.

**Why this works without `Location::caller()` or custom proc_macro2::Span:**

- `proc_macro2::Span` is *opaque* on stable Rust: you cannot construct a
  span pointing at an arbitrary file:line:col. Only `call_site()`,
  `mixed_site()`, and inherited spans from existing tokens are available.
- However, when rustc parses the generated .rs file as text, every token
  gets a fresh Span pointing at its file position. The dioxus-rsx
  proc-macro uses `quote_spanned!{ token.span() => ... }` to propagate
  those file positions into its expansion. Therefore rustc diagnostics
  carry precise (.rs file, line, col) coordinates — we just need to
  reverse-map them.
- Buff's only job is to maintain the (.rs position ↔ .buffhtml position)
  table. The codegen already has the .buffhtml spans; the post-format scan
  gives us the .rs positions. No upstream changes needed.

**Granularity achievable:**

| Construct                  | Per-token span? | Mapping quality      |
|----------------------------|-----------------|----------------------|
| `{expr}` interpolation     | YES             | exact token          |
| `attr={expr}` attribute    | YES             | exact token          |
| `on:event={closure}`       | YES             | exact token          |
| `<Component />` tag name   | YES             | exact token          |
| `{#each items as item}`    | partial         | block-level for body |
| Generated boilerplate      | NO              | block-level fallback |

This is **strictly better** than T121b mitigation #1 (filename translation
only) and meets T121b mitigation #2 (post-format line scan) for the
`.buffhtml` use case.

**§7 Trigger #1 — "`prettyplease` changes or new codegen backend needed":**
- **NOT TRIGGERED.** T121b already proved `prettyplease` preserves
  `rsx!{}` TokenStream. This spike re-confirmed it: all three experiments
  compiled through the existing syn/quote/prettyplease path. The
  post-format scan adds *no* changes to `prettyplease` — it reads
  prettyplease's output as text.

**§7 Trigger #2 — "Span mapping proves impossible without compiler hacks":**
- **NOT TRIGGERED.** Mapping is solvable with deterministic post-format
  text scan + side-table maintained during codegen. No rustc patches,
  no nightly features, no `proc_macro::Span` def-site hacks. **All work
  happens inside `buff-lang-codegen-buffhtml` and `buff-lang-cli/error_mapper.rs`.**

**No blockers identified. T133 may proceed without replan.**

================================================================================
DEGRADATION PATH (acceptable fallback if T133 runs out of time)
================================================================================

Per Oracle §5 risk #3 mitigation: "errors point to generated `.rs` with a
`TODO(buffhtml-span)` marker until proper mapping lands in T134."

**Concrete degradation:**

1. `buff-lang-codegen-buffhtml` emits `// TODO(buffhtml-span): path=Counter.buffhtml`
   as the first line of every generated .rs file (one-line change).
2. `buff-lang-cli/error_mapper.rs` translates the .rs filename in any
   rustc diagnostic to the .buffhtml filename (already half-built per
   T121b "Mitigation #1").
3. Diagnostics show `--> Counter.buffhtml:line:col` where `line:col` is
   the *generated .rs* position, with a banner noting "position refers
   to generated code; map back manually for now."

This is the **minimum viable** path — ships in days, not weeks. T134 then
implements the recommended post-format scan for precise mapping.

================================================================================
OPEN QUESTIONS DEFERRED TO T134
================================================================================

1. **Macro-expansion cascade filtering.** Experiment 3 showed that complex
   type errors cascade into dioxus-core / dioxus-html registry crates with
   their own spans. A polished error_mapper should detect and suppress
   these (or summarize as "see dioxus docs"). Defer heuristic to T134.

2. **Hot-reload (HMR) path.** Dioxus's `dx serve` recompiles on file
   change; Buff's transpile step must hook into the watch loop. Out of
   scope for T133 (which targets `buff build`/`buff run`), but the
   span-mapping strategy above is HMR-compatible.

3. **Tree-sitter grammar interaction.** The recommended `.buffhtml`
   tree-sitter grammar (deferred per §6) will need its own diagnostic
   surface for parser-level errors (e.g., unclosed `{#if}`). Those don't
   flow through rustc; they're emitted by `buff-lang-buffhtml-parser`
   directly with native spans. Orthogonal to this spike.
