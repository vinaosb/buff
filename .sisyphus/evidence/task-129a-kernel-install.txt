SUMMARY
-------
T129a ships the Jupyter wire-protocol SCAFFOLD (handshake only, NOT
real code execution) plus the `buff jupyter install` / `buff jupyter
start --connection-file <path>` CLI subcommands. Real Buff code
evaluation inside `execute_request` is T129b. Rich display, MIME
bundles, and `?`/`??` introspection are T129c.

CRATE
-----
`crates/buff-jupyter/` — pure-Rust lib crate (no C deps), edition
2021, version 1.0.0, license `MIT OR Apache-2.0`. Added to root
`Cargo.toml` workspace members (glob `crates/*`) + workspace dep
`buff-jupyter = { path = "crates/buff-jupyter" }`.

MODULES (`crates/buff-jupyter/src/`)
-----------------------------------
- error.rs        — JupyterError enum (thiserror) + From<io::Error>/From<serde_json::Error>
- connection.rs   — ConnectionFile parse + validate + endpoint builders
- wire.rs         — MessageHeader + WireMessage + PROTOCOL_VERSION = "5.3"
- hmac.rs         — sign/verify using hmac::Hmac<sha2::Sha256>, hex-encoded
- messages.rs     — KernelInfoReply::buff() (proto 5.3, language_info name=buff,
                    file_extension=.buff), ExecuteReply::stub_ok(),
                    ExecuteResult::stub(), StreamOutput::stub_stdout(),
                    ShutdownReply::ok(restart)
- kernelspec.rs   — KernelSpec::buff(argv) + write_kernel_json + install
                    (prefers `jupyter kernelspec install`; falls back to
                    direct write into <data_dir>/kernels/buff/)
- transport.rs    — ZmqTransport trait + ZmqSocketSet impl using pure-Rust
                    zeromq 0.4 (RouterSocket × shell/control + PubSocket +
                    RepSocket for hb; stdin NOT bound in T129a)
- kernel.rs       — Kernel<T: ZmqTransport> dispatch loop; handlers for
                    kernel_info_request / execute_request (stub) /
                    shutdown_request / interrupt_request (ack-only)
- lib.rs          — module wiring + public API surface +
                    run_kernel(path) + install()

CLI WIRING (`crates/buff-lang-cli/src/`)
----------------------------------------
- cli.rs             — Command::Jupyter { cmd: JupyterCmd } variant +
                       JupyterCmd::{Install, Start { connection_file }}
- commands/jupyter.rs — thin shim around buff_jupyter::install() /
                       buff_jupyter::run_kernel(); constructs a
                       multi-thread tokio runtime for the kernel loop
- commands/mod.rs    — `pub mod jupyter;`
- main.rs            — Command::Jupyter arm dispatching to commands::jupyter::run
- Cargo.toml         — `buff-jupyter.workspace = true`

DEPENDENCIES (root [workspace.dependencies])
--------------------------------------------
NEW:
- zeromq = "0.4"     (resolved to 0.4.1) — pure-Rust ZMQ transport
                      for the 5 Jupyter sockets. Verified to build
                      cleanly on this Windows host with no C deps.
                      Pin rationale: 0.4.x is the long-standing API
                      surface (Socket / SocketRecv / SocketSend traits
                      + RouterSocket / PubSocket / RepSocket /
                      ZmqMessage); 0.5+/0.6 ship identical surface
                      but bump MSRV unnecessarily for our pinned
                      1.95.0 toolchain — mirrors the rand-0.8 /
                      chrono-0.4 conservative-pin philosophy.
- bytes = "1"        (resolved to 1.12.1) — refcounted byte-buffer
                      crate zeromq uses for its frames. Already
                      transitively pulled via zeromq/tokio-util; pinned
                      explicitly so buff-jupyter can construct
                      multi-frame ZmqMessages without a conversion shim.
- buff-jupyter = { path = "crates/buff-jupyter" } — workspace path dep.

REUSED (already pinned via T124h/T124k/etc.):
- tokio (full)   — async runtime for the kernel loop + zeromq sockets
- serde + serde_json — wire-message / connection-file / content DTOs
- thiserror     — crate-local error enum
- uuid          — Uuid::new_v4() for kernel session_id + msg_id
- hmac + sha2   — HMAC-SHA256 signing/verification (T124k)
- hex           — hex encode of HMAC digests (T124h)

NO C DEPS. NO OPENSSL. NO LIBZMQ.

ACCEPTANCE CRITERIA — STATUS
----------------------------
Per plan L1882-1885, T129a has 3 acceptance criteria:

  [x] `buff jupyter install` registers kernel
      ─────────────────────────────────────
      VERIFIED OFFLINE. `buff jupyter install` was run on this build
      host and produced a valid kernel.json at
      C:\Users\vsbb1\AppData\Roaming\jupyter\kernels\buff\kernel.json
      (the canonical Windows Jupyter data-dir path).

  [ ] `buff jupyter install` appears in `jupyter kernelspec list`
      ────────────────────────────────────────────────────────────
      USER ACTION. This build host has NO `jupyter` installed (no
      `jupyter` / `jupyter-client` / `python` on PATH). Verifying
      discovery requires the user to install Jupyter on a host that
      has it, then run:
        1. `buff jupyter install` (or `cargo run -p buff-lang-cli -- jupyter install`)
        2. `jupyter kernelspec list`
        3. Assert output contains "buff"

  [ ] Kernel handshake works (`kernel_info_request` → reply)
      ───────────────────────────────────────────────────────
      PARTIALLY VERIFIED. The kernel_info_request → kernel_info_reply
      path is exercised end-to-end via the in-process mock transport
      in `crates/buff-jupyter/src/kernel.rs` (test
      `kernel_handles_kernel_info_request`). The wire-format and
      HMAC sign/verify logic is exercised by the integration tests
      under `crates/buff-jupyter/tests/`. LIVE verification against a
      real jupyter_client connection is a USER ACTION — requires
      Jupyter installed on the host.

  [ ] `jupyter console --kernel buff` connects without error
      ──────────────────────────────────────────────────────
      USER ACTION. Requires Jupyter installed on the host. After
      running `buff jupyter install`, the user should be able to:
        1. `jupyter console --kernel buff`
        2. Type `print("hello")` and see the stub reply:
           "execution not yet implemented (T129b)"
        3. Type `exit` to disconnect cleanly.
