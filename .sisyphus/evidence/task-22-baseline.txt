HOW THE BASELINE WAS CAPTURED
-----------------------------

The host is "windows-msvc-blocked" per the T22 task spec: the rustc
invocation finds VS 18 Insiders in the Windows registry, but that
install is missing `vcruntime.h` (the file exists only at
`C:\Program Files\Microsoft Visual Studio\18\Insiders\SDK\ScopeCppSDK\vc15\VC\include\vcruntime.h`
— a non-standard path that cc-rs cannot discover).

Consequences:
  - `cargo check -p buff-lang-cli --lib` fails: reqwest → rustls → ring's
    build script (cc-rs) cannot compile curve25519.c (C1083 vcruntime.h).
  - `cargo test -p buff-lang-cli --test bench_harness` fails: same chain.
  - VS 2022 Enterprise is installed alongside VS 18 Insiders; setting
    LIB + INCLUDE manually lets pure-Rust binaries link (verified with
    `rustc hello.rs`), but cc-rs ignores the env vars because it uses
    the registry-discovered toolchain (VS 18 Insiders) regardless.

Workaround used:
  - Wrote `examples/capture_t22_baseline.rs` inside buff-lang-codegen-rust
    (pure-Rust crate, no reqwest/ring in its dep graph).
  - Ran: `cargo run -p buff-lang-codegen-rust --example capture_t22_baseline
    -- examples .sisyphus/evidence/baseline-v1.25.json`
  - Output: 103-line JSON with all 6 fixtures measured. Per-fixture
    fields captured: lex_ms, parse_ms, typecheck_ms (=0, see below),
    codegen_ms, codegen_hash (sha256: + 64 hex chars, byte-deterministic),
    prefer_gpu_count, prefer_npu_count, function_count, error.
  - Back-end fields (clean_build_ms, binary_size_bytes,
    incremental_build_ms) are null because the standalone binary does
    NOT shell out to rustc (would hit the same MSVC blocker).

typecheck_ms = 0 explanation:
  The standalone binary depends on buff-lang-types transitively but
  does NOT expose TypeInferencer as a dev-dep (would require adding it).
  The full bench_harness.rs in buff-lang-cli DOES measure typecheck
  (it reuses the TypeInferencer pattern from check.rs::type_check_decls).
  When the bench_harness.rs runs on a non-MSVC-blocked host (CI),
  typecheck_ms will be populated. The codegen_hash is unaffected
  (typecheck is a read-only pass — same hash regardless).


DETERMINISM CHECK
-----------------

Codegen is byte-deterministic (project hard rule: syn/quote/prettyplease
via BTreeMap/BTreeSet). The harness was run twice consecutively; the
codegen_hash values were identical across both runs:

  ola              sha256:54840d4d7cc2ba54...  (stable)
  fibonacci        sha256:615d66cabf858f6b...  (stable)
  closures         sha256:cfb5c6c15d3d6c3e...  (stable)
  collections      sha256:88744f51a34bb914...  (stable)
  pattern_matching sha256:fc7053ccbaa7373f...  (stable)
  error_handling   sha256:f0471d7b256c6f09...  (stable)

These hashes are the identity signal T105 will diff against after the
god-class splits — any drift indicates a codegen change.
