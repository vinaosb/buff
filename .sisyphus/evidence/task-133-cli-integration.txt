## 3. Integration approach (where `.buffhtml` plugs into pipeline.rs)

The existing `.buff` pipeline is unchanged:

```
.buff source
    │
    ▼ read_to_string
    ▼ buff_lang_lexer::tokenize
    ▼ buff_lang_parser::parse
    ▼ buff_lang_codegen_rust::generate_rust
.rs source
    │
    ▼ pipeline::compile_rust_to_exe  (rustc --edition 2021)
native executable
```

The T133 `.buffhtml` path is a **sibling**, not a replacement:

```
.buffhtml source
    │
    ▼ read_to_string
    ▼ buff_lang_buffhtml_parser::parse       (3-mode lexer + recursive-descent)
    ▼ buff_lang_codegen_buffhtml::generate   (lowers AST → rsx!{} TokenStream)
.rs source (with __BUFF_SCRIPT_SOURCE const placeholder)
    │
    ▼ pipeline::inline_script_block          (NEW — T133 script-block pass-through)
        ├─ parse the .rs via syn::parse_file
        ├─ find + extract the const value
        ├─ remove the const item
        ├─ parse the script source as a syn::Block
        └─ prepend the block's stmts into the #[component] fn body
        └─ re-emit via prettyplease::unparse
final .rs source (script stmts inside component fn body)
    │
    ▼ pipeline::compile_buffhtml_rust_to_exe (span-aware rustc sibling)
        ├─ same rustc invocation + BuildMode flag selection
        └─ stderr → error_mapper::translate_buffhtml_rustc_errors
native executable
```

Two dispatchers route incoming paths:

- `pipeline::compile_to_rust_for_ext(file)` — picks `compile_to_rust` (for
  `.buff` or any non-`buffhtml` extension) or `compile_buffhtml_to_rust`
  (for `.buffhtml`); returns the generic `CompileOutput` (no span_map).
- `commands::build::build_single_file` directly branches on extension so
  it can use the span-aware rustc sibling for `.buffhtml` files.
- `commands::run::run` similarly branches; the `.buffhtml` path retains
  the SpanMap + buffhtml source so runtime panics can be reverse-mapped.
- `check::run_check_file` branches; the `.buffhtml` path runs parse +
  codegen without invoking rustc.

The `inline_script_block` step is the key T133 design call (see §5).

## 4. error_mapper span-translation approach

`error_mapper::translate_buffhtml_rustc_errors` implements the
span-mapping-spike VERDICT PASS recommendation
(`.sisyphus/evidence/task-133-span-mapping-spike.txt`):

1. **Filename translation (always):** Delegates to the existing
   `translate_rustc_errors` for path replacement (both native + forward-slash
   forms). This is the T121b mitigation #1 baseline.
2. **Span-aware line:col translation (when SpanMap non-empty):** Walks
   each `<buffhtml_file>:<rust_line>:<rust_col>` triple in the
   filename-translated stderr, queries `SpanMap::map_span(rust_line,
   rust_col)`, and — on hit — replaces the rustc line:col with the
   `.buffhtml` source line:col derived from a byte-offset → line:col
   lookup table (`byte_line_starts` + `byte_offset_to_line_col`).
3. **Graceful miss:** When the SpanMap returns `None` (no anchor
   precedes the queried position) OR the SpanMap is empty, the rustc
   line:col is preserved (still pointing at the `.buffhtml` filename —
   strictly better than the raw `.rs` path).

The `SpanMap` is the post-format side-table built by
`buff_lang_codegen_buffhtml::SpanMapBuilder::finalize`. It carries
`(RsLineCol, BuffHtmlSpan)` anchors sorted ascending; the binary-search
lookup finds the nearest preceding anchor in `O(log N)` per diagnostic.

The T121b `TODO(buffhtml-span)` marker for the empty-map case is
preserved in code comments at the fallback branch.

## 5. Script-block-handling rationale (T133 floor)

The decision record §3 example 1 shows `<script lang="buff">` blocks
containing `component Name = fn(...) -> Element:` shorthand — Buff syntax
that would need full transpilation. T133 floor explicitly defers this to
T134+ (decision record §6 DEFERS list: "Full LSP" + everything beyond
the floor grammar).

For T133 floor, the script block is treated as **Rust-in-script-block
pass-through**: the script source is spliced verbatim into the generated
`fn <Name>() -> Element { ... }` body, ahead of the `rsx!{}` expression.
The examples (`counter.buffhtml`, `todo_list.buffhtml`) use
Rust-compatible syntax (Dioxus 0.7 API: `use_signal`, `vec!`, etc.) that
the rustc+wasm32 build path consumes directly.

This is implemented in `pipeline::inline_script_block`:

1. The codegen crate (`buff-lang-codegen-buffhtml`) emits the script source
   as a top-level placeholder constant:

   ```rust
   #[doc = "buffhtml script block — extracted by buff-lang-cli"]
   const __BUFF_SCRIPT_SOURCE: &str = "<raw script source>";
   ```

   This keeps the generated `syn::File` syntactically valid Rust at the
   codegen layer (the script source isn't valid top-level Rust).

2. `inline_script_block` post-processes that placeholder:
   - Parses the generated `.rs` via `syn::parse_file`.
   - Walks items, finds `const __BUFF_SCRIPT_SOURCE`, extracts its
     `LitStr::value()` (handles all quoting forms — `"..."`, `r#"..."#`,
     escapes — via syn).
   - Removes the const item.
   - Parses the extracted script source as a `syn::Block`.
   - Finds the `#[component] fn <Name>() -> Element` item and prepends
     the script-block statements to its body (in front of the existing
     `rsx!{}` expression stmt).
   - Re-emits the file via `prettyplease::unparse`.

3. If no `__BUFF_SCRIPT_SOURCE` const is present (no `<script>` block in
   the source), `inline_script_block` returns the input unchanged — no
   syn round-trip overhead.

This keeps the codegen crate simple (it doesn't need to know about
script-block semantics) and concentrates the Rust-pass-through policy in
the CLI (the layer that knows about the downstream rustc invocation).

The error path is fail-loud: if `inline_script_block` cannot parse the
script source as Rust, it returns an `Err` with the message
"failed to parse `<script lang=\"buff\">` contents as Rust statements
(T133 ships Rust-in-script-block pass-through; full Buff-syntax
transpilation is T134+)".

## 8. Manual smoke verification (build agent side)

Beyond the unit + integration tests, I manually invoked:

```
$ cargo run -p buff-lang-cli -- build examples\counter.buffhtml
```

The generated `examples/counter.rs` (now cleaned up to avoid polluting
the workspace) was:

```rust
use dioxus::prelude::*;
#[component]
fn Counter() -> Element {
    let mut count = use_signal(|| 0);
    let increment = move |_| {
        count += 1;
    };
    rsx! {
        div { class : "counter", span { count }, button { on_click : increment, "+1", },
        },
    }
}
```

The script-block splicing worked exactly as designed: the `let mut
count = use_signal(|| 0);` + `let increment = move |_| { count += 1; };`
statements appear INSIDE the `fn Counter()` body, before the `rsx!{}`
expression. The `__BUFF_SCRIPT_SOURCE` const placeholder is gone. The
output is syntactically valid Rust (it round-trips through
`syn::parse_file` successfully).

The rustc step then fails with `E0433: failed to resolve: dioxus` — this
is the **expected** v0.5+ "single-file rustc cannot link large external
crates" limitation (same status as `async_demo.buff`, `extern_reqwest.buff`,
etc. in the existing examples table). The Cargo-project build path (Step
1–3 of the e2e recipe) is the supported workaround.
